CS3616: Week 4 — Code Quality & CI/CD

Module: CS3616 Software Engineering

You will need: VS Code, Python 3.10+, a GitHub account, and the CS3616_LabWeek4 folder.

Time: ~1.5 hours  ·  Format: individual or pairs

Goal: understand how a CI/CD pipeline enforces code quality automatically, and build a working one yourself. You will run the standard quality tools — ruff and mypy — locally, then configure a GitHub Actions pipeline that runs those checks and the test suite as quality gates on every push, blocking any change that fails to meet the bar.

This is the automated half of the workflow discussed in the lecture: automated checks catch mechanical issues so that human review can concentrate on design and business logic. The pull-request-plus-CI workflow you build here is standard practice in professional software teams, and being able to set up and read a pipeline is a skill employers expect.

All three parts are compulsory. The code under test (src/tax.py) and its test suite are given to you passing — this lab is about the quality tooling around the code, not the code itself.

A Run the quality tools locally Compulsory

Before automating anything, learn what each tool says when it's happy — and when it isn't.

1. Lint, format, type-check (the clean baseline)

ruff check src/ tests/          # -> All checks passed!
ruff format --check src/ tests/ # -> 3 files already formatted
mypy src/                       # -> Success: no issues found in 2 source files

--check makes ruff format report rather than rewrite — that's the mode CI uses, because CI must never silently change your code.

2. Introduce a lint violation, then auto-fix it

In src/tax.py, add an unused import just below the module docstring:

import os  # unused import

Re-run the linter:

ruff check src/
F401 [*] `os` imported but unused
  --> src/tax.py:12:8
help: Remove unused import: `os`
Found 1 error.
[*] 1 fixable with `--fix`.

The [*] means ruff can fix it safely. Let it:

ruff check src/ --fix           # removes the line
ruff check src/                 # -> All checks passed!

3. Introduce a type violation that no test catches

Tests only check the cases you thought of; types check the ones you didn't. In src/tax.py, change the return annotation from -> float to -> int:

) -> int:   # was: -> float

Run the tests — they still pass (the annotation doesn't change runtime behaviour). Now run mypy:

mypy src/
src/tax.py:55: error: Incompatible return value type (got "float", expected "int")  [return-value]
Found 1 error in 1 file (checked 2 source files)

allowance starts at 0.0 and is incremented by float literals, so its type is float — the -> int annotation is a lie, and mypy proves it without running the code. Restore -> float and confirm mypy is happy again.

Why this matters for AI-assisted coding

An LLM can generate a function whose annotation and body disagree. mypy catches that class of mistake automatically, on hand-written and generated code alike.

📝 Checkpoint: paste the F401 line and the mypy return-value line. Which did the test suite catch? (Neither — that's the point.)

B Build the GitHub Actions pipeline Compulsory

A GitHub Actions pipeline is a YAML file under .github/workflows/. We've given you a starter at .github/workflows/ci.yml with the two ruff jobs written; you'll add the mypy and pytest jobs so the pipeline runs lint, then type-check, then test.

How a pipeline is structured
  • A workflow contains jobs; each job runs on a fresh virtual machine.
  • Jobs with no needs: run in parallel.
  • needs: makes a job wait for the named jobs to succeed first — this is how you order the pipeline (lint → typecheck → test).
  • Each job is isolated, so every job must check out the code, set up Python and install dependencies itself.

1. Read the starter

Open .github/workflows/ci.yml. Note the shape of a job: it runs on a fresh ubuntu-latest machine and lists ordered steps — check out the code, install Python 3.12, install dependencies, then run the check.

ruff-check:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - run: python -m pip install -r requirements.txt
    - run: ruff check src/ tests/

2. Add the mypy job (typecheck)

Below the two ruff jobs, add a mypy job. The needs: line makes it wait for both lint jobs to pass first:

mypy:
  needs: [ruff-check, ruff-format]
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - run: python -m pip install -r requirements.txt
    - run: mypy src/

3. Add the pytest job (test)

Finally a pytest job that needs: [mypy], so the expensive tests run last and only if everything before passed:

pytest:
  needs: [mypy]
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - run: python -m pip install -r requirements.txt
    - run: pytest tests/ --cov=src --cov-branch --cov-report=term-missing -q

YAML is indentation-sensitive; if a job won't parse, compare it against the complete file in solutions/ci.yml.

4. Push it to GitHub

Create a repo on GitHub, then from the lab folder:

git init
git add .
git commit -m "ci: add GitHub Actions pipeline (lint, typecheck, test)"
git branch -M main
git remote add origin https://github.com/<you>/cs3616-labweek4.git
git push -u origin main

A new personal repository lets you push to main directly, so the commands above are enough. Some repositories have branch protection switched on (GitHub Settings → Branches), which blocks direct pushes to main and requires every change to go through a pull request. If yours is protected — or you want to practise the pull-request workflow from the lecture — put the change on its own branch and open a pull request to merge it into main:

git checkout -b ci/add-pipeline        # create and switch to a new branch
git push -u origin ci/add-pipeline     # push the branch to GitHub

GitHub then shows a button to open a pull request from that branch. The pipeline runs on the pull request, and you merge once it passes.

5. Watch it run

On GitHub, open the Actions tab, click the running workflow, and click any job to read its live log. A green run looks like this:

CI  ✓

ruff-check    ✓          }  run in parallel
ruff-format   ✓          }
mypy          ✓          (started only after both above passed)
pytest        ✓          (started only after mypy passed)

The pytest job log ends with the coverage table — src/tax.py … 100%, 12 passed.

Three questions to answer from the Actions tab
  1. Which two jobs run in parallel? (ruff-check and ruff-format — neither has needs:.)
  2. What status does pytest show while ruff is still running? (Queued/pending — needs: holds it back.)
  3. Where do you read the coverage %? (Inside the pytest job log.)

📝 Checkpoint: screenshot your green Actions run, and note which jobs ran in parallel versus in sequence.

C Break the pipeline, then fix it Compulsory

A quality gate is only useful if it actually blocks bad changes. In this part you make the pipeline fail on purpose, read the result, and restore it.

1. Introduce a violation and push

Add an unused import to src/tax.py (the same kind you fixed locally in Part A):

import sys  # unused
git add src/tax.py
git commit -m "test: introduce unused import to watch CI fail"
git push

2. Predict, then observe

Before you open the Actions tab, predict: which job fails? Which are skipped? Does ruff-format also fail? Then look:

CI  ✗

ruff-check    ✗ failed       F401 `sys` imported but unused
ruff-format   ✓ passed       (style is fine — the line is valid & formatted)
mypy          ⊘ skipped      (needs ruff-check, which failed)
pytest        ⊘ skipped      (needs mypy, which never ran)

Two lessons: parallel jobs are independent (ruff-format doesn't care about an unused import), and needs: means a failure upstream skips everything downstream — you never waste minutes testing code that already failed linting. That's fail-fast.

3. Restore green

Remove the import sys line, then:

git add src/tax.py
git commit -m "fix: remove unused sys import"
git push

Watch the new run go green end to end.

Stretch: make coverage a hard gate

Right now the pipeline reports coverage but doesn't enforce it. Add a floor to the pytest job and watch it block a thinly-tested change:

- run: pytest tests/ --cov=src --cov-branch --cov-fail-under=80 -q

Delete a couple of tests, push, and the job now fails with Coverage failure: total of … is less than fail-under=80. This is how a team turns "please keep coverage up" from a polite request into an enforced rule.

📝 Checkpoint: which single job failed, and which two were skipped? In one sentence, why is skipping them the right behaviour?

✓ Local ↔ CI: the same four commands Reference

Every CI job runs a command you can also run locally. Running check.sh before each push means CI reports problems you have already found and fixed, rather than surfacing them after the push.

Lintingruff check src/ tests/ruff-check

🧭 A green pipeline doesn't prove the code is correct — it proves it clears the bar the team agreed to. Review still owns design and business logic, as discussed in the lecture. CI just makes sure the mechanical checks are never skipped.
